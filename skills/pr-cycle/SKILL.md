# 需求到验收

## 固定入口与看板

默认运行栈为 **Claude Code + 官方 Ralph Loop 1.0.1 + Vibe Kanban 0.0.166**。开始循环前读取 [Claude Code 运行方式](references/claude-code.md)：Ralph 的 Stop hook 只维持当前协调者会话；Vibe 提供看板、独立 worktree 和 `CLAUDE_CODE` 工作者。只给协调者加载循环插件，不另写 AI 循环或叠加第二套调度器。普通读取本技能不会自动启动 Ralph。

看板版本和接入方式见 [看板接入](references/kanban.md)。不使用 `latest`：新版已退休本地项目看板，不能混用新版 cloud issue 接口。已有项目看板可在核实能力后映射同一流程，不另建重复事实来源。

执行前读取 [固定工作流](references/workflow.md)，按其中的状态门槛、并发上限与恢复协议推进。批次清单用 `scripts/kanban_batch.py` 验证、导入和查看就绪任务；脚本不代替风险定级、审查、人工审批或授权判断。派发实现任务时读取 [工作者契约](references/task-contract.md)。

协调者维护一张批次卡片和每个 PR 对应的任务卡片；批次关系写入描述，不假定上游支持原生父子任务。默认最多同时运行 3 个工作会话，可按预算与环境能力调整。协调者是批次看板状态和调度的唯一写者，工作者只推进领取的任务并回报证据。Ralph 默认使用显式的 20 次迭代上限，与每个 PR 最多三轮审查分别计数；等待人工审批、合并决定或无法继续时按运行说明安全交接，不为保持循环谎报完成。

协调者负责拆计划、派发和核对门槛；开发 AI 负责实现与自证；独立审查 AI 负责功能、代码质量与安全结论，不能由协调者或本 PR 开发者兼任。优先复用满足独立性要求的已有自动审查。合并及对应人工批准完成后，由单独的总结 AI 复盘，协调者核对其证据和规则候选。

## 变更风险与审批等级

每份计划派发前标注等级、依据及审批要求。等级描述变更风险，不是任务排期优先级；依据实际行为、影响范围和权限变化判断，不能仅按文件扩展名定级。

| 等级 | 典型变更 | 审批与 PR 规则 |
| --- | --- | --- |
| P0 | 架构调整、重大设计变更 | 单独向用户提交方案，用户明确批准后实施；使用独立 PR，最终版本仍须用户明确批准后才能合并 |
| P1 | 功能新增、功能行为变化 | 原则上一个完整功能一个 PR；至少一位具有项目审批权限的人类明确同意当前版本后才能合并 |
| P2 | 常规维护、低风险调整 | 需要人类审核通过；允许多个相关小变更组合成一个 PR，统一计划、验证和审批 |
| P3 | 低风险文档、注释、排版修改 | 可免人工常规审核；AI 仅自动完成开发、自证、独立审查及创建 PR，不自动合并，合并留给人工决定 |

混合变更按最高风险定级（P0 最高），P0 与普通变更拆开；P2 打包不能使 P1 功能变更降级。涉及安全规则、架构决策或执行权限的文档按实际影响定级。范围变化时重新核对等级与审批，原批准不覆盖新增范围。

所有等级都保留独立 AI 审查及三轮上限；P3 第三轮仍未通过也转人工。人工批准须记录批准者、对应方案或候选 SHA 和证据；方案批准、代码审核与合并决定分别记录，已有明确批准可以沿用，不重复索取。AI 通过、CI 绿灯、无评论或超时都不构成人工批准。项目已有更严格门槛仍须满足。

## 1. 复述并确认

复述用户目标、非目标、可观察验收条件、风险与预算约束。确认后进入实现；已有明确确认可以沿用，不重复索取授权。只补问真正影响实现的缺口。此流程不扩大工具、费用、推送、合并或部署权限。

## 2. 协调者直接拆分

- 协调者直接编写单 PR 粒度计划书，给出目标与非目标、变更边界、等级及依据、依赖、接口、负责人、验收项和审批要求，不再增加一层拆分代理。计划正文写入任务卡片或链接可读取文件，不能用项目总计划替代；每份计划只对应一个 PR。
- 一个计划对应一个独立 worktree、分支和真实 PR，具备完整可测试、可回滚的交付边界。P2 可在同一计划中组合多个相关小变更，逐项列出验收；独立任务并行，依赖任务按接口和顺序推进。固定目标分支及 base/head SHA；不同实现者不共写工作目录，不借用其他任务的分支。
- 每个 PR 的最终 additions + deletions 尽量不超过 1000 行，含测试、文档及生成文件；P2 组合也计入同一上限。超出先合理拆分；无法拆分则说明原因和规模，不能隐藏生成文件或硬拆半个功能。
- 多功能批次记录子 PR URL、依赖和独立验收项。可按项目已支持的堆叠 PR 或集成分支组织，核实实际能力；文档中的任务编号不能冒充真实 PR。
- 批量导入只创建待排队卡片。先核实依赖、资源冲突和可用槽位再启动；默认依赖任务交付完成、其提交进入下游固定 base 后才释放下游任务。

## 3. 实现者实际运行并自证

- 实现者完成实现、自检和关键用户路径运行后再交独立审查，不把主要运行验证和截图工作转交审查者。
- 记录精确 SHA、命令、环境、实际结果、未测项与风险。Bug 提供修复前复现及同路径修复后结果。构建、mock、真实服务验收分开报告。
- UI 变更给出关键步骤和结果的实际运行截图。截图放 PR 评论或附件，不提交代码分支。先核实上传工具支持的参数；上传受阻就报告阻塞，不编造附件 URL。
- 后端权限、数据或资金行为给出相应 API / 数据证据。测试使用隔离环境与合成数据，不泄漏凭据和个人数据。
- 无 UI 的规则或文档变更不伪造截图；检查范围、链接、规则一致性与 diff 即可。容器验证使用获授权的隔离环境，不擅自回退用户个人机器。
- PR 使用 [四节模板](references/pr-template.md)，每项证据关联实际提交。

## 4. 独立功能、代码质量与安全审查

- 优先复用仓库已配置的自动代码及安全审查，分别核实完成状态、覆盖 SHA 和未结发现。不额外派重复审查，也不重复手动触发。
- 未配置、未触发或未覆盖目标 SHA 时报告缺口；按已授权的备用方案处理，无备用授权时取得决策。没有评论不等于审查完成。
- 代码质量与安全按项目规则及 [REVIEW 示例](references/REVIEW.example.md) 中适用条款检查，分别记录结论。项目已有专门审查技能时可按需读取，缺失或未读取就说明；本工作流不依赖其他技能包。
- 独立审查者按单 PR 计划逐项核对功能验收、边界与失败路径、回归影响及运行证据；代码质量和安全分别出结论。记录审查者身份、覆盖 SHA、检查范围和未验证项；已有审查缺少功能覆盖时补齐该缺口，不能用质量扫描代替功能性审查。
- 审查只提出有证据的问题；外部实现可以比较和建议，未经用户采纳不改方案、迁移或加依赖。

## 5. 最多三轮收敛

一轮为审查反馈 → 修复或有证据的处置 → 验证。代码和安全汇总计轮，合计最多三轮；换代理、模型、重试、restack 或重开同一工作 PR 不重置。

首轮结合需求审完整 diff；第二、三轮检查新增 diff、已有问题闭环和受影响回归。以稳定问题 ID 合并同根因发现，记录位置、证据、首次轮次、状态、修复 SHA 与验证。误报用证据说明，不能为了消除评论做无意义修改。未经复核不标已解决。

同一问题两轮有效修复仍无进展可以提前升级。第三轮结束仍未通过时，立即停止该任务的自动返工，不进入第四轮；交协调者汇总证据、重新考虑方案并请求人工决策。保留 PR、工作区与证据，不等于取消整批；不得降门槛、自动通过或合并。

## 6. 组合版本检查

协调者核实最终必要 CI、冲突解决、共享状态和组合用户路径，记录每个子 PR SHA 与组合候选 SHA。各层通过不代表组合通过。rebase、冲突处理或实现变化后更新 SHA 映射，补受影响回归；旧证据不能冒充当前版本结果。

## 7. 分级人工审批与合并

PR 在进入独立审查前创建，用于保存证据；创建 PR 不等于允许合并。提供候选 SHA、适用的可运行产物、最短验证步骤、预期结果和剩余风险，按上述等级取得审批。P0 由用户批准最终版本，P1 至少一位有项目审批权限的人类同意，P2 人类审核通过；随后仅在实际合并授权范围内操作。无需手测的变更说明依据，不统一要求用户本人亲测所有 PR。

P3 在创建 PR 且独立审查、必要验证通过后结束自动开发流程，交接给人工决定合并；等待期间保持 `inreview`，不得自动合并或把人工批准记为通过。其他等级等待所需审批时也按运行说明安全交接。批准后代码改变须补受影响验证及相应人工确认；发布、部署按各自授权处理。

交付安装器、桌面应用或其他实际发布产物时，记录最终版本与文件哈希，验证实际下载、安装、启动到可用的完整路径，分别报告各平台结果、预览限制和未测项；项目已有发布验收规则时一并遵守。纯文案或内部小改动不强制执行整套发布验收。

## 8. 合并后复盘与规则沉淀

核实 PR 已实际合并且对应人工批准完成后，派发总结 AI 按 [返工总结](references/feedback.md) 复盘本次任务。每个 PR 保留复盘记录；批次可汇总，但不能以等待其他 PR 为由丢失已完成任务的经验。未合并或缺批准时只记录当前事实与待办，不宣称完成合并后复盘。

总结 AI 提出踩坑、根因、修复与验证证据及规则候选；机械检查优先进入测试/CI，长期可判断规则进入 `REVIEW.md`。总结者只给候选 diff 与理由，经协调者核对原始证据、用户确认并走正常变更流程后才写入知识库，不自动修改规则或降低门槛。

## 模型和成本策略

按可配置的任务难度、风险、预算与可用能力选择模型：确定性检查优先脚本；明确局部实现优先低成本档；复杂诊断、设计和高风险判断选择能力适配档；证据整理使用较低成本档。开始时说明所选角色、成本边界与升级条件，不把特定型号视为公开环境默认可用。

先排除环境故障与缺上下文，再决定是否升级。超过预算、增加付费调用或越出授权能力时先取得对应决策；不无限重试。总结会话同样计入工作会话并发与预算；因资源受阻时记录待复盘任务及恢复条件。

## 项目规则接入

Claude Code 的项目入口使用 `CLAUDE.md`，明确要求按任务读取相关技能和 `REVIEW.md`。已有 `AGENTS.md` 时在 `CLAUDE.md` 中明确引用并要求读取，不假定 Claude 原生自动加载它；其他客户端沿用其实际支持的项目入口。`REVIEW.md` 只放可判断的长期项目规则，逐轮发现与证据留在 PR。缺文件或约束冲突应报告，不臆造机制。Vibe 工作者不会自动继承协调者的 `--plugin-dir`，启动前按工作者契约提供可读的绝对路径或完整必要规则。

创建项目规则时可按需参考 [通用 REVIEW 示例](references/REVIEW.example.md)，仅保留实际适用、可验证的条款。

## 批量委托示例

```text
读取 pr-cycle，按已确认需求建立本批看板，编写每 PR 一份计划并标注 P0～P3 等级。
并发上限 3，先运行无依赖且资源不冲突的任务；受阻任务留在看板并写明恢复条件。
实现者完成实际运行自证后再进入代码与安全审查，合计最多三轮。
交付组合候选版本和分级审批材料；P3 自动化止于创建 PR，不自动合并。
合并及人工批准完成后派发总结 AI 提出 REVIEW.md / CI 候选，沿用当前已授予的操作权限。
```
