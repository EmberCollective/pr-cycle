# 需求到验收

## 固定入口与适用范围

执行前读取 [受控工作流](references/workflow.md)，派发时读取 [工作者契约](references/task-contract.md)。本技能规定协调行为，不扩大工具、费用、推送、合并或部署权限。

项目固定 Vibe Kanban 0.0.166；工作者复用本机 CLI。当前受控流程只允许 Claude Code，自动 PR 路径只支持单仓库 GitHub 项目。Codex 接入、其他托管平台、多仓库和真实远端验收的边界见工作流页面。

Ralph Loop 1.0.1 可让协调者在同一会话继续推进，默认最多 20 次迭代；它不会自动批准计划或合并。加载技能、打开 Claude 或启动看板都不等于启动 Ralph。使用前读取 [Claude Code 运行方式](references/claude-code.md)。

## 变更风险与审批等级

规划 Agent 给出等级、定级理由、范围、验收及 PR 拆分，人类只审核批准，不手工代填计划或等级。等级是风险，不是优先级。P0～P3 均须人类批准当前计划后实施，并在最终审查栏批准当前候选版本后才能执行最终合并。

| 等级 | 典型变更 | PR 安排 |
| --- | --- | --- |
| P0 | 架构调整、重大设计变更 | 独立计划和 PR，明确影响与回退方式 |
| P1 | 新功能或行为变化 | 按完整可验证的功能拆分 PR |
| P2 | 常规维护、低风险调整 | 允许相关子 PR 按依赖堆叠并集成，组合版本重新双审 |
| P3 | 低风险文档、注释、排版 | 可以简化计划和验证，但不跳过计划批准、双审和最终人工批准 |

混合变更按最高风险定级，P0 与普通改动分开；P2 打包不能使 P1 变更降级。涉及权限、安全规则或架构决策的文档按实际影响定级。新增范围需要更新计划，旧批准不能覆盖新增内容。

## 计划与实施分工

- 先明确目标、非目标和可观察验收条件；已有明确授权可以沿用，尚有歧义时只补问影响实施的缺口。看板中的计划批准仍须绑定保存后的当前计划版本。
- 规划与主实施沿用同一个 Agent 会话。规划本身包含分析和审查，不新增规划审查 Agent；人类批准前不能实施。开始授权并批准计划后，后台按依赖自动完成子实施、主实施、双审、返工、PR 和 P2 集成复审，无需逐阶段点击或保持浏览器打开。
- 实施允许使用已规划的子 Agent。每个子 Agent 使用独立工作区和分支，按声明的依赖顺序领取任务；不得让多个实现者同时写同一工作目录。
- 只有 P2 可以发布并组合多个子 PR；其他等级的实施子 Agent 作为协作者，由主实施会话汇总提交后统一审查。记录真实分支、base/head 和子 PR URL，不用任务编号代替 PR。
- 每个 PR 尽量保持可独立测试、回滚，并控制在 1000 行增删内。无法合理拆分时说明规模及原因，不隐藏生成文件或硬拆半个功能。
- 批次脚本只提供就绪建议。协调者核对跨任务依赖、预算和资源；后台限制受控工作会话最多 3 个并发，但不负责其他服务的会话或完整跨批次资源锁。

## 实施与自证

实现者运行与验收相关的路径，记录命令、环境、实际结果和对应提交。Bug 保留修复前复现与修复后结果；构建、mock、真实服务验收分别报告。UI 提供关键交互截图，非 UI 改动不伪造截图。

子任务结束不代表主任务完成。主实施者检查组合效果；非发布子任务的实际提交须汇入主工作分支。所有实施者完成提交并给出证据后，才进入功能审查。

实施执行器按已批准计划运行，关闭 CLI 交互审批，允许计划内工具执行；规划和两项审查仍保持只读工具限制。执行器按已批准计划冻结的提示词和输入启动。修改项目默认提示词或任务覆盖只影响下一次计划批准，不能静默替换已批准任务的执行指令。

## 两项独立审查

功能性审查和安全性审查分别使用独立会话，不能由主实施者、任何实施子 Agent 或对方的审查会话兼任。功能审查核对需求、边界、代码质量和测试证据；安全审查核对权限、输入及数据风险。

当前审查配置只允许读取和检索，不执行测试或修改代码。缺运行证据就打回实施补齐；安全审查发现问题同样打回实施，不允许审查者自行修复后批准。自动化扫描可以作为证据，但不替代这两项受控审查结果。

每项结论绑定实际候选版本。返工、未提交修改、需求变化或集成产生的新版本会使相应通过记录失效；修复后重新双审。记录问题位置、证据、处置、修复版本和未测项，不为消除评论做无意义修改。

后台在当前计划自上次明确恢复以来累计三次未通过的阶段结果后暂停自动返工。核对问题后由人类明确恢复，再开始下一段自动尝试；历史记录保留。费用上限由协调者管理。暂停只停止新派发，不终止已运行 Agent。

## PR、集成与最终人工审查

受控流程在两项审查通过后创建或更新 PR。P2 多子 PR 在独立集成工作区按依赖组合，重新进行功能性和安全性审查后发布总 PR；这个中间步骤不等于合入最终目标分支。

规划审查和最终审查使用独立面板：前者展示任务、Agent 计划及等级依据并批准计划；后者展示真实 PR、当前候选版本、功能与安全审查证据并批准最终版本。所有等级最终进入最终审查栏。人类批准当前版本后，仍需明确执行合并；远端未确认合并成功时不能标记完成。创建 PR、CI 绿灯、没有评论和超时都不等于人工批准。

安装器或其他发布产物仍须按项目要求验证实际交付路径，发布和部署另按已有授权处理。合并后可以安排独立总结 AI 提出规则候选，但当前服务不会自动执行复盘或修改知识库。

## 项目规则与交接

提供项目 `CLAUDE.md`、已有 `AGENTS.md`、适用 `REVIEW.md` 和本技能的可读取路径或必要内容。Vibe 工作者不会自动继承协调者通过 `--plugin-dir` 加载的技能；不能把文件链接当作已经读取。缺规则或权限时说明具体缺口。

交接需区分代码完成、双审通过、计划批准、最终批准、PR 已创建和实际已合并。保留任务与会话 ID、当前版本、运行中进程、阻塞原因及恢复步骤。关闭终端、断网或取消 Ralph 不证明工作者已停止。

应用门禁不提供同一操作系统用户下的安全身份隔离；自动测试也不等于真实模型和 GitHub 远端流程已经验收。以 [支持范围与验收边界](references/workflow.md#支持范围与验收边界) 为准。
